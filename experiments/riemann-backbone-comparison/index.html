03 / Experimental purpose

Which comparison answers which question?

M1 is a mechanism-control candidate, not the claimed faster final architecture. These contrasts have different levels of causal precision.

ContrastQuestion and evidenceInterpretation boundary
B0 → M1

Can our edge-conditioned operator family replace RiEMann's per-layer SE(3) K/V path while retaining equivariance, pose quality, and task success? Measure its runtime too, without predicting a speed ordering.

An end-to-end backbone replacement, not an operator-only causal test: the new initial lift and other implementation details may differ from B0.

M1 → M2

After the same initial lift, are geometry-conditioned edge K/V needed again at every layer? Compare step time, inference latency, equivariance, and quality at matched convergence.

Attribute a difference to the edge-conditioning schedule only if the lift, fibers, graph, depth, attention score, heads, normalization, training, and implementation budget are matched.

B0 → M2

Does the final candidate improve both training-to-quality and complete-policy inference latency against a rerun of the official baseline without unacceptable quality loss?

This establishes the practical outcome, not which architectural change caused it. Use M1 to interpret the mechanism.

Shared M1/M2 test design: one identical relative-edge lift and typed starting fiber; the same four attention-layer interfaces and all policy components. The planned switch is per-layer edge-conditioned K/V in M1 versus nodewise equivariant linear K/V in M2. Q stays nodewise in both. If this matching cannot be implemented, report M1/M2 as a multi-factor comparison rather than a clean ablation.

Expected from design

Less repeated edge-kernel work in M2

M2 should need fewer steerable edge-kernel applications than M1 at the same graph and depth. This is a computational mechanism, not a guaranteed end-to-end speedup.

Must be measured

Both faster training and inference

Compare training step time, time to matched validation quality, and model-only plus full-policy latency on the same GPU. M1 versus B0 has no assumed ordering.

Must not be lost

Equivariance and task quality

Check type-0/type-1 residuals, pose error, and paired closed-loop success. A faster but less effective policy does not validate the original objective.

05 / Personal experiment report

RiEMann B0 / M1 / M2 study

Measured / complete

Research question. Can our SO(3)-equivariant backbone make the RiEMann manipulation policy faster in both training and inference, without materially reducing pose accuracy or task success?

Identification strategy. Reproduce B0, then replace only the three network backbones. All three candidates use the same full-scene XYZ/RGB input, radius graphs, ROI protocol, typed heads, pose construction, losses, data split, and execution stack.

Models and provenance

B0 is the official RiEMann SE(3)-Transformer policy. M1 and M2 were implemented, trained, and evaluated here as matched proposed backbones: both use a relative-edge lift; M1 retains edge-conditioned K/V in every attention layer, while M2 uses nodewise equivariant linear Q/K/V after the lift. The public Atlas experiment is a report of this local implementation, not a claim from the RiEMann authors.

Purpose of M1

M1 checks whether our per-layer edge-conditioned replacement can preserve the baseline's equivariance and task quality. More importantly, paired with M2 it tests whether repeated directional edge conditioning earns its extra cost after both start from the same typed features. B0 versus M1 is a practical architecture comparison; M1 versus M2 is a schedule ablation only after their shared components are matched and verified.

Frozen comparison protocol

All models used 2,500-point preprocessing, batch 1, FP32, the same 8/2 trajectory split, Phi 200 epochs, manipulation 500 epochs, and seeds 0/1/2. Held-out prediction used the learned Phi center, not GT ROI. The paired simulation study used 5 conditions (T, NI, NP, DO, ALL), 20 scene seeds, the same Panda/MPlib/SAPIEN execution stack, and a shared success rule.

Measurement contract

We report held-out translation/rotation error, rotation equivariance residuals, warm-up-and-synchronized p50/p95 latency, peak memory, training wall time, Wilson confidence intervals, exact paired McNemar tests, and policy/planner/execution failure categories. The 600 timing pairs quantify runtime repeatability; only three independent training seeds support cross-run claims.

Decision rule

The dual-speed claim requires faster training to matched quality and lower complete-policy inference latency on the same hardware, while pose quality and task success meet thresholds fixed before final testing. A reduction in theoretical edge operations alone is not sufficient. If one metric fails, report the partial outcome rather than averaging it away.

Why the speed result is statistically meaningful

Paired bootstrap over the same seed and repeat index. A positive delay difference means B0 took longer.

M2 / speed

Large and consistent

The 95% interval for M2's speedup stays above 3.5× in both timing scopes. This is a hardware-measured result on the four L20Z setup, not an inference from parameter count.

M1 / trade-off

Smaller is not faster here

M1 has far fewer parameters and memory use than B0, yet repeated edge-conditioned messages make its measured latency higher. The kernel schedule matters more than the parameter total.

Quality boundary

Do not average away the failure

M2's speed gain coincides with much worse rotation error and difficult-condition success. The original dual-speed-and-quality claim is therefore only partially supported.
